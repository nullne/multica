# 任务执行与验证循环 功能清单（产品视角）

> 当一个 issue 被指派给 agent 时，系统会为它创建一个**任务（task）**并交给某个 runtime 去执行。
> 这个领域由四部分组成——**任务的生命周期**（从排队到完成、失败或取消）、**agent 干活时的实时流式输出**、
> **由独立的 verifier agent 对照 acceptance criteria 做验证与返工的闭环**，以及**任务进展与 issue 状态的自动同步**。

这是一份自顶向下、面向用户能力的功能清单，用来核对产品功能是否齐全。

## 1. 任务是什么

- [ ] 当一个 issue 被指派给 agent 后，系统会为这次工作创建一个任务（task），代表"让 agent 做这件事"的一次执行。
- [ ] 每个任务都关联到一个具体的 issue，用户可以从 issue 追溯到它产生的任务。
- [ ] 每个任务携带一个 provider（例如 claude、codex），决定它需要由哪种 agent runtime 来执行。
- [ ] 用户无需手动操作执行细节：指派 agent 这个动作本身就会驱动后续的整套执行流程。

## 2. 任务的生命周期

- [ ] 任务会经历一组清晰、可观察的状态，用户在任意时刻都能知道工作进行到哪一步：
  - [ ] **queued（已排队）**：任务已创建并已选定一个 runtime，等待被该 runtime / daemon 领取。
  - [ ] **dispatched（已分派）**：任务已被某个 runtime / daemon 领取（认领），但还没真正开始执行。
  - [ ] **running（执行中）**：agent 正在干活。
  - [ ] **completed（已完成）**：agent 报告这次执行完成。
  - [ ] **failed（失败）**：执行中出错（崩溃、超时、runtime 丢失、产出无法解析等）。
  - [ ] **cancelled（已取消）**：被用户或系统主动取消。
- [ ] 任务只会分派给支持该 agent 所需 provider 的 online runtime；找不到匹配的 online runtime 时任务保持排队，等到有 runtime 上线再执行。
- [ ] 同一 issue 可以一次性取消其全部活跃任务（例如重新指派时清理旧任务）。
- [ ] 用户可以取消单个任务，取消会即时反映到界面上，正在显示的实时执行卡片随之清除。
- [ ] 执行出错时任务进入失败状态并保留错误信息，同时把错误作为一条系统说明回贴到 issue 上，便于用户判断发生了什么。
- [ ] 受 agent 的并发上限（max concurrent tasks）约束：同一 agent 同时执行的任务数不超过其配置，超出的任务继续排队。

## 3. 实时流式输出（看着 agent 干活）

- [ ] agent 工作过程中产生的内容会被实时推送给正在查看的用户，无需刷新即可看到进展。
- [ ] 流式输出区分了不同类型的消息，让用户能读懂 agent 到底在做什么：
  - [ ] **文本**：agent 的自然语言输出（思考、说明、结论）。
  - [ ] **工具调用**：agent 调用了某个工具，以及它传入的内容。
  - [ ] **工具结果**：工具返回给 agent 的结果。
  - [ ] **错误**：执行过程中发生的问题。
- [ ] 这些消息会被持久化保存，用户事后回看任务时仍能完整重现 agent 的工作过程。
- [ ] agent 可以在执行途中上报进度（当前步骤 / 总步骤 + 一句话摘要），界面据此显示推进情况。
- [ ] 每一次任务状态变化（dispatched / completed / failed / cancelled）都会实时通知到界面，用户能即时看到任务从排队到结束的推进。
- [ ] agent 在干活时其自身状态会在 idle 与 working 之间自动切换，用户能从 agent 列表看出它当前是否正忙。
- [ ] 输出在落库与广播前会做敏感信息脱敏处理。

## 4. Acceptance criteria 与验证闭环

- [ ] 用户可以为一个 issue 额外指定一个 **verifier agent**（验证 agent），与执行 agent（assignee）分开，从而开启自动验收闭环。
- [ ] 验证闭环只在"把 issue 指派给执行 agent"这种场景下启用；通过评论 @ 提及触发的任务走普通流程，不进入闭环。
- [ ] verifier 必须不同于执行 agent，否则不构成独立验收。
- [ ] 开启闭环后，系统会先确定一组结构化的 acceptance criteria（验收标准）：
  - [ ] 若 issue 还没有验收标准，先由 verifier agent 跑一个任务，根据 issue 内容起草一份验收标准。
  - [ ] 起草出的验收标准需要**人工确认**后才会继续；在确认前，执行 agent 不会开工。
  - [ ] 验收标准确认通过后，系统才把执行任务派给执行 agent，并把验收标准一并带给它参考。
- [ ] 执行 agent 报告完成后，系统会**自动派一个验证任务给 verifier agent**：让它对照验收标准核对产出。
- [ ] 验证给出结构化结论：通过 / 不通过、总体说明，以及（不通过时）逐条未满足项及原因。
- [ ] 验证结论会作为评论回贴到 issue 上并实时推送到界面，用户能看到结论与具体反馈。

## 5. 返工与最大验证轮数

- [ ] 验证不通过时，系统会自动为同一个 issue 创建一个**返工任务**派回执行 agent，并把验证反馈（未满足项、说明）注入到返工提示中，让 agent 针对性修正。
- [ ] 返工评论会自动 @ 执行 agent，把"请修复后再次提交"的回流动作做成闭环，无需用户手工搬运信息。
- [ ] 返工后会再次自动验证，形成"执行 → 验证 → 返工 → 再验证"的循环，每失败一轮轮次加一。
- [ ] 验证循环有最大轮数上限（默认 5 轮，可在 issue 上配置）：达到上限后系统**停止自动返工**，并贴一条系统说明告知已停止，交给人来介入。

## 6. 任务进展与 issue 状态自动同步

- [ ] 用户不需要手动同步两边的状态——验证闭环会自动带动 issue 状态变化：
  - [ ] 验证通过时，若 issue 当前处于"待审核（in review）"，自动转为"完成（done）"；其他状态不强行覆盖。
  - [ ] 验证通过、不通过、返工等关键节点都会把对应的 issue 更新实时广播到界面。
- [ ] 执行过程中 issue 的进行中状态由 agent 通过 CLI 自行管理，系统不在任务开始/完成时擅自改写，避免与 agent 的真实判断冲突。
- [ ] agent 产出的 PR 链接、分支等会自动作为 issue 的外部关联回写并展示，用户可从 issue 直接跳转。
- [ ] 这样无论是看板还是 issue 详情，用户看到的 issue 状态与关联始终与 agent 的真实进度一致。

## 7. 权限与 workspace 隔离

- [ ] 任务、任务消息、验证结论以及实时事件都归属于具体的 workspace，用户只能看到自己所属 workspace 内的执行情况。
- [ ] 实时事件按 workspace 定向推送；当一个 issue 已被删除、无法确定其 workspace 时，相关事件不会被广播出去，避免泄漏到其他 workspace。
- [ ] 只有对相应 issue 有访问权限的成员，才能查看由它产生的任务、流式输出与验证反馈。
- [ ] 取消任务等操作受 workspace 成员权限约束，跨 workspace 无法相互干预对方的任务。
- [ ] runtime / daemon 只能领取并执行属于其所在 workspace、且匹配其 provider 的任务，不能越过 workspace 边界访问无关的工作。
