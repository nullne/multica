# 评论与讨论 功能清单（产品视角）

> 评论让团队和 AI 队友围绕每个 issue 展开讨论：**写评论、回复别人、@ 提及人或 agent、用表情回应**。
> 它由四部分组成——**评论与回复**、**@提及（既能通知人，也能直接把活交给 agent）**、
> **表情回应**，以及**谁能写、谁能改**。

这是一份自顶向下、面向用户能力的功能清单，用来核对产品功能是否齐全。

## 1. 在 issue 下评论

- [ ] 用户可以在任意一个 issue 下写评论，参与该 issue 的讨论。
- [ ] 一个 issue 可以有任意多条评论，按发表时间从早到晚排列。
- [ ] 评论内容不能为空。
- [ ] 评论可以由 member 撰写，也可以由 agent 撰写——agent 在 issue 上的留言和人的评论一样，是讨论的一部分。
- [ ] 每条评论都会标明作者是谁、是 member 还是 agent，以及发表和最后修改的时间。

## 2. Threaded 回复

- [ ] 用户可以针对某一条已有评论发表回复，形成有层级的讨论串，而不是平铺成一长串。
- [ ] 回复只能挂在同一个 issue 下的评论上，不能跨 issue 引用。
- [ ] 每条评论会显示它收到了多少条回复，方便快速判断哪条讨论更热闹。

## 3. @提及（Mention）

- [ ] 在评论正文里用 `@handle` 即可提及一个 workspace 内的 member 或 agent。
- [ ] 同一条评论里可以提及多个人或 agent。
- [ ] 同一个对象在一条评论里被重复提及时只算一次，不会重复通知或重复触发。
- [ ] 提及的 handle 不区分大小写。
- [ ] 提及一个不存在的 handle 会被自动忽略，不会报错或产生无效提及。
- [ ] member 既可以用名字提及，也可以用邮箱前缀提及；agent 用其名字提及。
- [ ] 评论展示时会把其中的提及解析成对应人或 agent 的当前名字。

### 3.1 提及 member —— 通知

- [ ] 当评论提及某个 member 时，该 member 会在 Inbox 收到一条提及通知，并能定位到对应的 issue 和评论。

### 3.2 提及 agent —— 直接派活

- [ ] 当评论提及某个 agent 时，系统会自动为该 agent 在这个 issue 上创建一个任务，让它接手处理。
- [ ] 这种由提及触发的任务会标记触发来源为 "mention"，并记录是哪条评论触发的，便于把 agent 后续的工作追溯回最初的那条评论。
- [ ] agent 自己写的评论同样会被识别其中的提及——因此一个 agent 可以在评论里 @ 另一个 agent，把工作接力交给对方，形成 agent 之间的协作链路。

## 4. 表情回应（Reaction）

- [ ] 用户可以给任意一条评论加上 emoji 表情回应，快速表态而不必另写一条评论。
- [ ] 对同一条评论、同一个 emoji 再次操作即可取消自己的回应（点一下加、再点一下取消）。
- [ ] 同一条评论上相同的 emoji 会被聚合展示，显示总数以及都有谁回应过。
- [ ] 一条评论可以同时存在多种不同的 emoji 回应。

## 5. 编辑与删除

- [ ] 评论作者本人可以编辑自己写过的评论，修改后会更新最后修改时间。
- [ ] 评论作者本人可以删除自己的评论。
- [ ] 只有评论的原作者能编辑或删除该评论，其他人不能改动别人的评论。

## 6. 实时同步

- [ ] 新评论、评论被编辑或删除、表情回应的变化，都会实时同步给 workspace 内正在查看的其他成员，无需手动刷新。

## 7. 权限与 workspace 隔离

- [ ] 评论、回复、提及和表情回应都归属于具体的 issue，并被限定在该 issue 所属的 workspace 内。
- [ ] 只有能访问对应 workspace 的成员才能查看和参与该 issue 的讨论。
- [ ] @提及只能命中同一个 workspace 内的 member 和 agent，无法提及外部的人或其他 workspace 的对象。
- [ ] 编辑和删除受作者限制：仅原作者本人可操作自己的评论。
