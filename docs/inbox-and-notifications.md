# Inbox 与通知 功能清单（产品视角）

> Inbox 是每个用户在 workspace 里的个人通知中心：当与你相关的事情发生时（issue 被分配给你、状态变化、有人评论、被 @ 提及、任务失败等），
> 系统会在你的 Inbox 里生成一条通知。这个领域由三部分组成——**Inbox 里的通知项与阅读管理**、**谁会收到通知（subscriber 机制）**、
> 以及**通知往哪里送达（站内 + Telegram 渠道）**。

这是一份自顶向下、面向用户能力的功能清单，用来核对产品功能是否齐全。

## 1. Inbox 是什么

- [ ] 每个用户在 workspace 里有一个属于自己的 Inbox，集中展示所有与自己相关的通知。
- [ ] Inbox 通知项与具体的 issue 关联，用户可以从通知直接跳转到对应 issue 的详情。
- [ ] 通知按时间倒序排列，最新的事件排在最前面。
- [ ] 同一个 issue 上的多条通知会被合并成一条（Linear 风格，每个 issue 一个条目），展示其中最新的一条，避免同一 issue 反复刷屏。
- [ ] 通知项会显示触发者（actor）的头像与名字，让用户知道是谁做的这件事。
- [ ] 通知项会带上 issue 的当前状态图标，方便用户判断该 issue 现在进展到哪一步。

## 2. 通知项的类型

- [ ] 当一个 issue 被分配给你时，你会收到「被分配」通知。
- [ ] 当 issue 的 assignee 发生变化（改派 / 取消指派）时，相关人会收到「改派 / 取消指派」通知。
- [ ] 当 issue 状态发生变化时（如从进行中变为已完成），你会收到「状态变更」通知。
- [ ] 当 issue 的 priority 变化时，你会收到「优先级变更」通知。
- [ ] 当 issue 的 due date 变化（设置 / 修改 / 移除）时，你会收到「截止时间变更」通知。
- [ ] 当有人在你关注的 issue 下发表新评论时，你会收到「新评论」通知，并能看到评论摘要。
- [ ] 当有人在 issue 描述或评论里 @ 提及你（或 @all）时，你会收到「被提及」通知。
- [ ] 当有人对你的评论添加表情回应时，你会收到「表情回应」通知。
- [ ] 当与你相关的 agent 任务完成或失败时，你会收到「任务完成 / 任务失败」通知。
- [ ] 通知会带上触发它的上下文信息（哪个 issue、谁触发的、改成了什么值），帮助用户判断是否需要处理。

## 3. 通知的严重程度（severity）

- [ ] 每条通知会被标记一个严重程度，区分「仅供知晓」与「需要处理」两类。
  - [ ] info：纯告知性事件（如新评论、状态变更、被提及、表情回应），知道即可。
  - [ ] action_required：需要用户介入的事件（如 issue 被指派给你、任务失败）。
- [ ] 用户可以借助严重程度快速分辨哪些通知是必须立刻跟进的。

## 4. 阅读与清理

- [ ] 每条通知有「已读 / 未读」状态，未读项有明显标记（小圆点、加粗）。
- [ ] 用户可以看到当前未读通知的数量，用于在导航上展示计数 / 小红点。
- [ ] 点击一条通知即自动把它标记为已读，并在右侧打开对应的 issue 详情。
- [ ] 通知项支持「归档（archive）」：归档后从 Inbox 列表中消失，但不影响 issue 本身。
- [ ] 用户可以一键把所有通知标记为已读。
- [ ] 用户可以一次性归档全部通知。
- [ ] 用户可以一次性归档「所有已读」的通知，只保留未读。
- [ ] 用户可以一次性归档「对应 issue 已完成 / 已取消」的通知，清理掉已经收尾的事项。
- [ ] 已读与归档都是个人维度：同一个 issue 的事件，不同用户各自维护自己的阅读状态。

## 5. 谁会收到通知（subscriber 驱动）

- [ ] 通知不是发给所有人，而是发给「订阅了该 issue 的人」（subscriber）。
- [ ] 系统会自动把相关用户加为 issue 的 subscriber，无需手动设置：
  - [ ] issue 的创建者自动订阅。
  - [ ] issue 的 assignee 自动订阅（包括被改派后的新 assignee）。
  - [ ] 在描述或评论里被 @ 提及的人自动订阅。
  - [ ] 在 issue 下发表过评论的人自动订阅。
- [ ] 用户可以查看某个 issue 当前的 subscriber 列表。
- [ ] 用户对自己主动产生的动作不会收到自我通知（不会被自己的操作打扰）。
- [ ] 只有 member 类型的 subscriber 会进入个人 Inbox，agent 不会收到站内通知。
- [ ] subscriber 机制保证用户只收到与自己真正相关的事件，避免噪音。

## 6. 站内实时更新

- [ ] 新通知到达时，Inbox 会实时更新，无需手动刷新页面。
- [ ] 未读计数会随通知的产生与已读 / 归档操作实时变化。
- [ ] issue 状态变化时，Inbox 中对应通知的状态图标会同步更新。

## 7. 通知渠道（站外推送）

- [ ] 除了站内 Inbox，用户可以配置外部通知渠道，把通知推送到 Inbox 之外。
- [ ] 用户可以查看自己当前已配置的通知渠道列表。
- [ ] 渠道可以被启用或停用，停用后不再向该渠道推送。
- [ ] 当 Inbox 产生新通知时，符合条件的事件会同步推送到该用户已启用的渠道。

## 8. Telegram 推送

- [ ] **个人 Telegram 通知**
  - [ ] 用户可以把自己的 Telegram（chat）绑定为一个通知渠道。
  - [ ] 绑定后，发给自己的相关通知会以消息形式推送到 Telegram。
  - [ ] 用户可以启用 / 停用，或删除自己的 Telegram 通知绑定。
- [ ] **Workspace 级 Telegram 群组**
  - [ ] workspace 可以配置一个 Telegram 群组聊天，作为团队公共的通知出口。
  - [ ] 管理员可以查看群组配置是否已设置、对应的 chat 以及是否启用。
  - [ ] 管理员可以新增 / 更新 / 删除 workspace 的 Telegram 群组配置，并随时启用或停用。
- [ ] 推送的 Telegram 消息包含可点击的 issue 标题、事件类型标签，以及（如有）事件正文摘要，引导用户回到对应 issue。
- [ ] Telegram 推送在后台异步发送，投递失败不会影响站内通知的正常生成。

## 9. 权限与 workspace 隔离

- [ ] Inbox 通知严格按用户隔离：用户只能看到发给自己的通知，看不到他人的 Inbox。
- [ ] 所有通知、subscriber 关系与渠道配置都归属于具体的 workspace，跨 workspace 之间互不可见。
- [ ] 用户只能在自己是成员的 workspace 内查看和管理通知。
- [ ] 个人通知渠道（如个人 Telegram 绑定）只属于用户本人，由本人配置与删除。
- [ ] workspace 级的 Telegram 群组配置属于 workspace 设置，受 workspace 成员关系约束。
- [ ] 标记已读、归档通知、解除绑定等操作只能针对属于自己 / 自己所在 workspace 的数据执行。
